실행 전 확인사항과 지원 범위

실행 경로별 준비물, 입력 계약, 지원 경계와 검증 단계를 확인합니다.

SDK 2026.4 계열 / 버전별 표기약 4분원고
이 장의 목차
실행 경로를 먼저 선택한다장치 실습을 시작하기 전에예제와 수치의 범위구현에 의존하기 전에 확인할 경계출처

CPU에서 숫자만 확인하는 예제는 RNGD 없이 실행할 수 있다. 장치 실습은 사용할 경로의 SDK·컴파일러·장치 조건을 먼저 맞춘다. 아래 표에서 자신의 예제가 어느 경로인지 찾으면 준비할 도구를 고를 수 있다.

아래 표에서 사용할 경로의 준비물을 고른다. ‘파일을 만들었다’, ‘읽었다’, ‘NPU에서 호출했다’, ‘답이 맞았다’는 순서대로 확인할 별개의 단계다.

실행 경로를 먼저 선택한다

경로 준비할 입력 프로그램을 만드는 단계 실행을 맡는 계층 관련 장
공식 Furiosa-LLM 지원 모델의 자산, 호환 FXB와 실행 설정 공식 모델 빌드·컴파일 Furiosa-LLM과 공식 런타임 03 스택, 14 서빙

예를 들어 덧셈 프로그램과 ReLU 프로그램이 있어도 어느 쪽을 먼저 실행할지 설명이 더 필요하다. 같은 크기의 입력 중 어느 것을 가중치로 쓸지도 알려 줘야 한다.

이 값 연결과 실행 순서를 담는 것이 실행계획이다. EDF 파일만 여러 개 있을 때와 모델 코드·연결 설명이 함께 있을 때의 차이는 05장에서 작은 덧셈으로 다룬다.

장치 실습을 시작하기 전에

  1. SDK·컴파일러·드라이버·펌웨어 버전을 각각 기록한다. Python 패키지 버전 하나로 전체 환경을 대표하지 않는다. 장치 상태를 읽는 방법은 03장에 있다.
  2. 예제의 입력 shape·dtype·stride, 인수 순서와 출력 구조를 확인한다. 패키지와 외부 가중치는 같은 모델에서 만들어야 한다.
  3. 컴파일 대상 PE 구성과 실행할 장치 구성을 맞춘다. 카드 수, PE 수, 연산 융합은 서로 다른 설정이다.
  4. 새 프로세스에서 적재한 뒤 CPU 기준값과 NPU 출력을 비교한다. 사전검사 통과, 컴파일 성공, NPU 실행, 수치 일치는 각각의 확인 단계다.
  5. 정확도를 확인한 뒤 최초 준비와 반복 요청을 따로 측정한다. 비동기 제출 직후가 아니라 결과 사용에 필요한 완료 지점까지 잰다. 17장 측정 실습을 참고한다.

TCC가 호스트 메모리를 많이 사용해 실패한다면 먼저 컴파일 작업 하나로 재현한다. 동시 worker 수를 줄이고, 어느 영역·shape에서 메모리가 늘어나는지 확인한 뒤 영역 경계를 조정한다. EDF를 무조건 잘게 나누면 제출과 중간 텐서 비용이 늘 수 있다. 이 절충은 06장 버킷과 컴파일 비용, 07장 최적화에서 다룬다.

이 핸드북의 정적 사이트 검사와 Python 구문 검사는 장치 검증을 대신하지 않는다. 성능 표에는 기존 기록인지 설명용 계산인지 표시한다. CPU로 확인할 수 있는 기초 예제와 장치가 필요한 실습은 구분해 제공한다. 이 핸드북에서 새 RNGD 실행이나 성능 측정을 수행한 것은 아니다.

구현에 의존하기 전에 확인할 경계

항목 현재 의존할 수 있는 내용 별도 검증이 필요한 부분
ATen 지원 고정 소스의 등록·변환 규칙과 검증 기록 모든 overload·shape·dtype의 장치 정확도
SDK EDF와 opt Image 각 경로의 로더와 호출 계약 포맷·ABI 호환성과 교차 적재
fxbX와 공식 FXB 각 형식을 지원하는 소비자의 실행 경로 공식 Furiosa-LLM이 임의 fxbX를 직접 수용하는 기능
커스텀 모델의 서빙 단일 모델의 패키지 적재·호출 배칭, KV 상태, sampling, 취소·오류와 worker 연결
여러 NPU 해당 경로가 지원하는 장치·병렬 설정 상태 분리, 통신 비용과 처리량·지연의 확장성

공개되지 않은 compiler pass의 선택 알고리즘, SDK와 opt의 내부 합류 지점 등은 각 장에서 확인 가능한 경계까지만 설명한다. 용어를 다시 찾을 때는 용어 사전, 구현을 따라갈 때는 각 장의 고정 소스 링크를 이용하면 된다.
