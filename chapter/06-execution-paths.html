Chapter 06

FXB, FuryNo5, fxbX의 실행 경로

같은 NPU를 쓰더라도 요청을 받아 어떤 프로그램을 호출할지 결정하는 주체가 다릅니다. 실행 경로를 확인할 때는 파일 확장자와 함께 로더와 실행 계획을 확인하세요.

누가 실행 순서를 정할까?

경로준비와 실행
공식 FXB + Furiosa-LLM모델 설정·토크나이저·가중치를 별도로 읽고, 호환되는 FXB에서 사전 컴파일된 커널을 로드합니다. Furiosa-LLM이 요청을 배치로 묶고 Prefill·Decode 단계별로 버킷과 호출할 프로그램을 선택하며 KV Cache를 관리합니다.
FuryNo5 직접 실행prepare_model_direct가 PyTorch 모델을 export하고 고정 입력 조건에서 SDK로 컴파일하거나 호환되는 .runnable을 재사용합니다. 장치 활성화 때 SDK Runnable과 고정 가중치를 올리고, 호출마다 입력을 보내 실행한 뒤 결과를 CPU로 가져옵니다.
fxbX의 .fxbx 패키지예를 들어 runnable-dag-v1 형식은 execution_plan.json에 단계와 텐서 연결을 저장합니다. 로더가 각 SDK Runnable을 역직렬화하고, fxbX 실행기가 계획대로 호출합니다. fxbx run은 이 프로젝트의 CLI입니다.
fxbX의 EDF 기반 GraphFXB단일 EDF 경로는 저장된 graph_plan으로 EDF와 입력 바인딩을 찾습니다. 다중 EDF 경로는 계획 스키마에 따라 ExecutionFXB가 실행합니다. 외부 가중치와 입력·출력을 연결하고, 마지막으로 사용한 중간 텐서를 해제하며, 완료 확인 뒤 상태를 갱신합니다.

예를 들어 furiosa-llm serve MODEL --fxb model.fxb에서 MODEL은 모델 설정과 가중치 등을, --fxb는 컴파일된 번들을 지정합니다. fxbX가 읽는 .fxb 패키지가 공식 검사 도구에서 열려도, Furiosa-LLM이 그 모델을 서빙하려면 해당 아키텍처와 실행 계약을 지원해야 합니다.

실행 그래프와 EDF

실행 그래프는 어떤 프로그램이 어느 텐서를 소비하고 어디에 결과를 넘기는지 표현합니다. 예를 들어 행렬 곱셈이 h를 만들고, ReLU가 h를 읽어 y를 만든다면 h가 두 단계를 잇는 의존성입니다. EDF는 컴파일된 장치 프로그램입니다. fxbX의 모델 수준 실행 계획은 각 EDF의 입력·출력에 어떤 텐서를 연결할지 기록합니다.

Two EDFs with an explicit plan
x, w → [matmul.edf] → h → [relu.edf] → y

One EDF with both operations
x, w → [matmul_relu.edf] → y

실행 그래프 파일 없이 EDF 하나 실행하기

  1. 컴파일 조건과 맞는 SDK·장치 토폴로지를 준비하고, EDF의 입력 순서·shape·dtype·layout과 가중치 바인딩을 생산 기록에서 확인합니다.
  2. SDK의 Runnable.from_serialized_edf가 EDF를 전처리하여 실행 가능한 객체로 만듭니다. 호스트 관점에서는 입력과 출력이 연결된 단일 실행 노드로 취급할 수 있습니다.
  3. 장치에 프로그램과 입력을 올려 호출하고, 완료된 출력을 가져옵니다. 여러 EDF의 조합이라면 생산자가 순서, 중간 텐서, 외부 가중치, 상태 갱신을 정의하고 fxbX 같은 로더가 그 계획을 검증한 뒤 실행합니다.
# Assume device topology and ordered NPU inputs are already configured.
from pathlib import Path
import furiosa.torch as ft

ir = ft.ir.Runnable.from_serialized_edf(Path("model.edf").read_bytes())
program = ft.Runnable(ir).to("furiosa:0")
outputs = program(*device_inputs)
어떤 그래프가 만들어질까?위 코드에서 확인할 수 있는 결과는 단일 EDF의 SDK 실행 객체입니다. 여러 EDF의 모델 그래프나 KV Cache 연결을 복원하려면 별도의 실행 계약이 필요합니다. SDK 내부에서 어떤 자료 구조를 만드는지는 이 로더 호출만으로 확인할 수 없습니다.

버킷, Prefill, 타이밍

버킷(bucket)은 특정 입력 범위에 맞춰 미리 컴파일해 둔 커널 변형입니다. 공식 FXB에는 토큰 단위 연산용 버킷과 Attention 버킷이 있으며, 후자는 배치와 Attention 길이, 입력 토큰 수 등을 기준으로 구분합니다. fxb show BUNDLE에서 버킷을 보고 fxb inspect BUNDLE에서 입출력 시그니처를 확인할 수 있습니다.

Prefill은 입력 프롬프트를 처리해 KV Cache를 채우는 단계입니다. Decode는 그 캐시를 재사용해 다음 토큰을 생성하는 단계입니다. 여기서는 PF를 Prefill이라는 뜻으로 읽습니다. 프로파일에 약어가 표시되면 해당 도구에서 사용하는 이벤트 이름도 확인하세요.

비교 예시빨라지는 조건과 느려지는 조건
입력 120토큰, 128·512 버킷둘 다 호환되고 패딩 구간까지 처리하는 구현이라면 128 쪽이 불필요한 작업을 줄일 수 있습니다. 더 큰 버킷이 배치 처리에 유리한 경우도 있으므로 TTFT와 처리량을 함께 측정합니다.
긴 Prefill과 동시 Decode긴 Prefill을 한 번에 처리하면 작업 제출 횟수는 적을 수 있지만, 뒤의 Decode가 기다리면 토큰 간 지연이 커집니다. 지원되는 스케줄러에서 작은 청크로 나누면 Decode에 실행 기회를 줄 수 있으며, 너무 작으면 제출과 동기화 비용이 늘어납니다.
NPU Task는 짧고 요청은 느림작은 Task 사이에 긴 공백이 반복되면 호스트 호출·대기·복사를 추적합니다. 장치 타이밍, 큐 대기, H2D/D2H, 완료까지의 요청 시간을 구분하세요. 비동기 호출의 반환 시각은 실행 완료 시각과 다를 수 있습니다.

버킷이 너무 성기면 큰 변형에 맞추는 비용이 커질 수 있습니다. 너무 촘촘하면 컴파일할 변형 수와 번들 크기가 늘어납니다. 자주 들어오는 입력과 배치부터 맞추고, Prefill은 TTFT, Decode는 TPOT, 서비스 전체는 p95와 처리량을 같은 요청 분포에서 비교하세요.

TCL을 어느 크기로 묶어 EDF를 만들까?

먼저 연속해서 쓰는 연산을 한 후보로 만듭니다. 예를 들어 matmul → bias → ReLU가 같은 데이터 타입과 배치를 쓰고 중간값을 다른 곳에서 소비하지 않는다면 한 TCL 영역으로 컴파일해 봅니다. 융합되면 제출 횟수와 중간 텐서의 메모리 쓰기·읽기를 줄일 수 있습니다.

재사용과 입력 형상이 갈리는 곳을 분할 후보로 삼습니다. 예를 들어 큰 Attention과 MLP의 경계 또는 대표 버킷별로 복제되는 구간을 비교합니다. 경계를 지나는 텐서가 작고 배치 변환이 적은 곳이 유리합니다. 반대로 큰 활성값이 여러 분기에 살아 있는 구간에서는 하나의 거대한 EDF가 컴파일 시간과 메모리 부담을 키울 수 있습니다.

지나친 분할의 비용을 확인합니다. add·reshape·activation마다 EDF를 호출하면, 장치에서 중간 텐서를 유지하더라도 호스트 제출·바인딩·스케줄링이 반복됩니다. 중간값을 메모리에 써야 하는 경계에서는 전송 비용도 따를 수 있습니다. 동일 EDF를 재사용하면 파일 수는 줄지만 호출 횟수는 그대로일 수 있습니다.

가령 단계별 제출에 20 µs가 걸린다고 가정하면, 직렬 호출에서 100단계의 제출 비용은 2 ms, 10단계는 0.2 ms입니다. 이는 설명용 계산입니다. 같은 EDF를 순차 제출하는 실행기에서 묶음 제출로 바꾸면 호스트 비용을 줄일 수 있고, TCL을 합쳐 EDF를 다시 만들면 장치 내부의 중간값 저장과 호출 횟수까지 달라질 수 있습니다. 두 변경을 따로 측정하세요.

비교할 후보 세 가지같은 입력과 정밀도로 연산별 EDF, 인접 연산을 묶은 EDF, 더 큰 블록 EDF를 비교합니다. CPU 기준값과 오차, 컴파일 시간·최대 RSS, 경계 텐서 크기, 호출 횟수와 NPU Task 사이 공백, 완료까지의 p95를 기록해 분할점을 고릅니다. 호출 수가 줄어도 컴파일에 실패하거나 메모리 사용이 크게 늘면 이전 분할점부터 다시 비교합니다.

TCC 컴파일이 호스트 메모리를 많이 쓸 때

furiosa-tcc가 TCL을 EDF로 변환할 때 큰 영역이나 여러 동시 컴파일이 호스트 RAM 또는 컨테이너 메모리 한도를 넘길 수 있습니다. 종료 코드나 SIGKILL만으로 OOM 여부를 판단하기 어려우므로, 컴파일 로그와 최대 RSS, Linux cgroup의 memory.events에서 oom_kill 변화 등을 함께 확인합니다. 컴파일러가 출력한 스케줄·레이아웃 오류, 시간 초과, 실행 중 NPU HBM 부족도 각각 다른 원인입니다.

  1. 동시 컴파일을 1개로 낮추고 같은 TCL·버킷을 재현합니다. 공식 FXB 빌드에서는 해당 버전의 --concurrency를 확인하세요.
  2. 단일 작업도 한도를 넘으면 문제 버킷과 영역을 찾아 의존성이 적고 중간값이 작은 지점에서 나눕니다.
  3. 양쪽 EDF의 바인딩과 출력 정확도를 검증한 뒤 NPU에서 실제 요청 시간을 비교합니다.
