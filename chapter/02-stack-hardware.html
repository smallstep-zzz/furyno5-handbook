Chapter 02

소프트웨어 스택과 하드웨어

NPU 연산 장치가 데이터를 기다리는 동안에는 계산도 지연됩니다. 데이터를 어느 메모리에 두고 얼마나 자주 옮기는지가 실행 시간에 영향을 줍니다.

SDK 설치와 버전 확인

공식 SDK는 compiler, runtime, profiler, quantizer와 Python binding을 묶어 제공합니다. 먼저 버전을 고정하고, 예제가 실제 장비에서 돌아가는지 확인하세요.

python -m venv .venv
source .venv/bin/activate
pip install furiosa-sdk
pip show furiosa-sdk
furiosa-smi --help
주의: 이름이 비슷해도 같은 계층이 아닙니다furiosa-opt의 vISA kernel 예제, 공식 SDK의 TCL API, FuryNo5의 계획·실험 코드는 서로 다른 계약입니다. 공개 코드를 보고 임의로 “같은 compiler에 들어간다”고 가정하지 마세요.

NPU 최적화가 메모리 문제인 이유

  • 작은 연산을 너무 많이 쪼개면 kernel launch와 DMA 비용이 계산보다 커집니다.
  • layout이 맞지 않으면 transpose·repack이 매번 생깁니다.
  • FP32를 끝까지 유지하면 bandwidth와 capacity를 압박합니다.
  • 동적 shape는 compile cache와 scheduling을 어렵게 만듭니다.

권장 순서는 정확도 확인 → shape/layout 고정 → fusion → dtype/quantization → batch/concurrency입니다.

RNGD의 DMA 경로

직접 메모리 접근(DMA)은 전송 엔진이 출발 메모리에서 데이터를 읽어 목적지에 쓰는 방식입니다. RNGD에서는 호스트와 장치 사이의 전송과 장치 내부 전송에 각각 다른 엔진을 씁니다.

  1. 입력 전송(H2D) — 호스트 RAM의 입력을 PCIe DMA로 NPU의 고대역폭 메모리(HBM)에 올립니다.
  2. 장치 내부 전송 — 예를 들어 Tensor DMA로 HBM에서 칩 내부의 데이터 메모리(DM)로 계산에 쓸 타일을 옮깁니다. Tensor Unit의 Fetch가 데이터를 가져와 연산에 공급하고, Commit이 결과를 DM에 씁니다.
  3. 결과 전송(D2H) — 호스트에서 결과가 필요하면 예를 들어 Tensor DMA로 DM에서 HBM으로 옮긴 뒤 PCIe DMA로 호스트 RAM에 가져옵니다. 결과를 이어서 NPU에서 쓸 경우 장치에 유지할 수 있습니다.
전송 결과를 언제 읽을까?전송을 비동기로 제출하면 요청을 넣은 시점과 데이터가 도착한 시점이 다릅니다. 그 데이터를 처음 사용하는 연산은 전송 완료 이후에 실행해야 합니다. 위 순서는 공개 Tensor Unit 입출력 예제를 바탕으로 한 경로입니다.

Python에서 호스트↔NPU 전송 확인

RNGD가 보이는 Furiosa PyTorch SDK 환경에서 dma-probe.py를 내려받아 python dma-probe.py로 실행합니다. 4 MiB 정수 텐서를 왕복시켜 값이 같은지 검사하고, 각 방향의 중앙값을 출력합니다.

from statistics import median
from time import perf_counter

import torch
import furiosa.torch as ft

device = torch.device("furiosa:0")
host = torch.arange(1024 * 1024, dtype=torch.int32)
samples = [[], []]

# Warm up the SDK, allocator and transfer path.
for _ in range(3):
    warm = host.to(device).cpu()
    ft.current_stream(device).synchronize()

for _ in range(10):
    ft.current_stream(device).synchronize()
    start = perf_counter()
    npu = host.to(device)
    ft.current_stream(device).synchronize()
    uploaded = perf_counter()

    result = npu.cpu()
    ft.current_stream(device).synchronize()
    downloaded = perf_counter()

    torch.testing.assert_close(result, host, atol=0, rtol=0)
    samples[0].append((uploaded - start) * 1000)
    samples[1].append((downloaded - uploaded) * 1000)

print(f"{host.numel() * host.element_size():,} bytes each way")
print(f"H2D median: {median(samples[0]):.3f} ms")
print(f"D2H median: {median(samples[1]):.3f} ms")

이 값에는 SDK 호출, 목적지 메모리 할당, 동기화가 포함됩니다. 전송과 계산을 겹치는 실험에서는 단계마다 동기화하면 겹침이 사라질 수 있으므로, 배치 끝에서 완료를 기다리고 프로파일 타임라인에서 복사 구간을 비교하세요.

Rust에서 DMA 컨텍스트를 직접 선택

아래는 furiosa_opt_std::prelude::*를 쓰는 공개 예제의 핵심 호출입니다. SDK 예제처럼 device와 host를 준비하고, 반환형으로 HBM의 Chip·Element 매핑을 지정합니다. 장치 커널에서는 input의 타입과 축에 맞춰 DM 매핑을 정합니다.

// Inside an async host function with axes A and B defined
let hbm: HbmTensor<i8, m![A], m![B]> =
    host.to_hbm(&mut device.pdma).await?;
let _host_copy: HostTensor<i8, m![A, B]> =
    hbm.to_host(&mut device.pdma).await?;

// Inside the fetch_commit_simple device kernel; use its declared axes
let dm = input.to_dm::<Cluster, m![A / 16], m![A / 8 % 2, A % 8, B]>(
    &mut device.tdma,
);

Tensor DMA 내부에서 일어나는 일

  1. 컴파일 — 출발·목적 텐서의 매핑에서 전송 반복 횟수와 주소 간격(stride)을 계산합니다.
  2. 읽기와 쓰기 — 읽기 시퀀서는 출발 주소를, 쓰기 시퀀서는 목적지 주소를 같은 반복 순서에서 진행합니다. 두 주소의 간격을 다르게 설정하면 같은 논리 원소를 다른 물리 배치에 저장할 수 있습니다.
  3. 완료와 소비 — 다음 연산은 자신이 읽는 데이터가 준비될 때까지 기다립니다. Tensor Unit의 Fetch와 Commit은 계산 파이프라인 쪽의 입출력 단계입니다.

상황왜 느린가개선 방법
연산마다 중간 결과를 CPU로 복사PCIe를 왕복하고 다음 NPU 작업도 기다립니다.예를 들어 행렬 곱셈 뒤 활성화 함수까지 NPU에서 실행하고 최종 출력만 가져옵니다.
작은 전송을 자주 제출하고 매번 완료 대기복사할 데이터에 비해 요청 처리와 동기화 비용이 커집니다.지연 시간 목표를 지키는 범위에서 입력을 묶습니다. 독립적인 작업은 다음 타일을 옮기는 동안 현재 타일을 계산하도록 겹칠 수 있습니다.
연산 사이에 데이터 배치를 반복해서 변환같은 데이터를 다시 읽고 쓰면서 메모리 대역폭을 사용합니다.앞 연산의 출력 배치와 뒤 연산의 입력 배치를 맞춥니다. 칩 내부 SRAM 간 복사가 필요하다면 Tensor DMA와 Tensor Unit의 Fetch/Commit 경로를 비교합니다.

변경 효과를 보려면 같은 입력으로 호스트→장치 전송, NPU 계산, 장치→호스트 전송과 전체 응답 시간을 확인하세요. 전송과 계산을 겹치면 구간별 시간이 중복되므로 전체 시간도 직접 측정합니다.
