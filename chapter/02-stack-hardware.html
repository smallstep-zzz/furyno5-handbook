Chapter 02

소프트웨어 스택과 하드웨어

NPU 연산 장치가 데이터를 기다리는 동안에는 계산도 지연됩니다. 데이터를 어느 메모리에 두고 얼마나 자주 옮기는지가 실행 시간에 영향을 줍니다.

SDK 설치와 버전 확인

공식 SDK는 compiler, runtime, profiler, quantizer와 Python binding을 묶어 제공합니다. 먼저 버전을 고정하고, 예제가 실제 장비에서 돌아가는지 확인하세요.

python -m venv .venv
source .venv/bin/activate
pip install furiosa-sdk
pip show furiosa-sdk
furiosa-smi --help
주의: 이름이 비슷해도 같은 계층이 아닙니다furiosa-opt의 vISA kernel 예제, 공식 SDK의 TCL API, FuryNo5의 계획·실험 코드는 서로 다른 계약입니다. 공개 코드를 보고 임의로 “같은 compiler에 들어간다”고 가정하지 마세요.

NPU 최적화가 메모리 문제인 이유

  • 작은 연산을 너무 많이 쪼개면 kernel launch와 DMA 비용이 계산보다 커집니다.
  • layout이 맞지 않으면 transpose·repack이 매번 생깁니다.
  • FP32를 끝까지 유지하면 bandwidth와 capacity를 압박합니다.
  • 동적 shape는 compile cache와 scheduling을 어렵게 만듭니다.

권장 순서는 정확도 확인 → shape/layout 고정 → fusion → dtype/quantization → batch/concurrency입니다.

RNGD의 DMA 경로

직접 메모리 접근(DMA)은 전송 엔진이 출발 메모리에서 데이터를 읽어 목적지에 쓰는 방식입니다. RNGD에서는 호스트와 장치 사이의 전송과 장치 내부 전송에 각각 다른 엔진을 씁니다.

  1. 입력 전송(H2D) — 호스트 RAM의 입력을 PCIe DMA로 NPU의 고대역폭 메모리(HBM)에 올립니다.
  2. 장치 내부 전송 — 예를 들어 Tensor DMA로 HBM에서 칩 내부의 데이터 메모리(DM)로 계산에 쓸 타일을 옮깁니다. Tensor Unit의 Fetch가 데이터를 가져와 연산에 공급하고, Commit이 결과를 DM에 씁니다.
  3. 결과 전송(D2H) — 호스트에서 결과가 필요하면 예를 들어 Tensor DMA로 DM에서 HBM으로 옮긴 뒤 PCIe DMA로 호스트 RAM에 가져옵니다. 결과를 이어서 NPU에서 쓸 경우 장치에 유지할 수 있습니다.
전송 결과를 언제 읽을까?전송을 비동기로 제출하면 요청을 넣은 시점과 데이터가 도착한 시점이 다릅니다. 그 데이터를 처음 사용하는 연산은 전송 완료 이후에 실행해야 합니다. 위 순서는 공개 Tensor Unit 입출력 예제를 바탕으로 한 경로입니다.

전송이 병목이 되는 경우

상황왜 느린가개선 방법
연산마다 중간 결과를 CPU로 복사PCIe를 왕복하고 다음 NPU 작업도 기다립니다.예를 들어 행렬 곱셈 뒤 활성화 함수까지 NPU에서 실행하고 최종 출력만 가져옵니다.
작은 전송을 자주 제출하고 매번 완료 대기복사할 데이터에 비해 요청 처리와 동기화 비용이 커집니다.지연 시간 목표를 지키는 범위에서 입력을 묶습니다. 독립적인 작업은 다음 타일을 옮기는 동안 현재 타일을 계산하도록 겹칠 수 있습니다.
연산 사이에 데이터 배치를 반복해서 변환같은 데이터를 다시 읽고 쓰면서 메모리 대역폭을 사용합니다.앞 연산의 출력 배치와 뒤 연산의 입력 배치를 맞춥니다. 칩 내부 SRAM 간 복사가 필요하다면 Tensor DMA와 Tensor Unit의 Fetch/Commit 경로를 비교합니다.

변경 효과를 보려면 같은 입력으로 호스트→장치 전송, NPU 계산, 장치→호스트 전송과 전체 응답 시간을 확인하세요. 전송과 계산을 겹치면 구간별 시간이 중복되므로 전체 시간도 직접 측정합니다.
