Chapter 08

furiosa-smi를 언제 쓰는가

실행 전에는 furiosa-smi로 NPU가 보이는지 확인하세요. 실행 중에는 장치 상태를 확인하고, 어느 연산이나 전송에서 시간이 걸렸는지는 프로파일러 기록에서 찾습니다.

furiosa-smi --help
furiosa-smi info
furiosa-smi status
furiosa-smi status --interval 1
명령은 설치된 버전에 따라 다를 수 있습니다위 예시는 방향을 잡기 위한 대표 형태입니다. 먼저 furiosa-smi --help로 현재 subcommand와 출력 형식을 확인하세요.

재현 가능한 benchmark

  1. driver·SDK·model artifact의 버전을 기록합니다.
  2. 다른 작업이 장치를 함께 쓰는지 확인하고, 초기화 영향을 줄이기 위해 몇 번 먼저 실행합니다. 준비 실행(warm-up)은 본 측정에서 제외합니다.
  3. 고정된 prompt, input shape, output token 수로 반복합니다.
  4. furiosa-smi 상태와 앱 로그의 timestamp를 맞춥니다.
  5. median, p95, TTFT, TPOT, tokens/s, power/utilization을 함께 저장합니다.
# 공식 benchmark 도구의 방향을 확인하는 예시
furiosa-perf run --backend furiosa-llm --hardware-type npu ...
# vLLM 경로도 별도 backend로 비교할 수 있음
furiosa-perf run --backend vllm --hardware-type npu ...

숫자를 읽는 법

버킷과 타이밍에서 요청 시간과 NPU Task 시간을 구분하는 예를 볼 수 있습니다.

관측값무엇을 알려주나낮거나 높을 때 질문
TTFTprefill·초기 queue 비용prompt 길이, compile cache, batch?
TPOTdecode 반복 속도KV Cache layout·memory bandwidth?
p95측정값의 95%가 이 시간 이하동시성·GC·host sync?
NPU utilization장치가 바쁜 정도장치가 다음 작업이나 데이터 전송을 기다렸는지 확인합니다. DMA 병목 사례를 참고하세요.

최적화 전후에는 “평균 latency만 좋아졌다”가 아니라, 정확도·p95·전력·utilization까지 같은 실험 조건에서 비교해야 합니다.

마무리공식 FXB baseline → custom region → profiler/smi 상관분석 순서를 지키면, 개선이 실제 NPU 최적화인지 쉽게 설명할 수 있습니다.
