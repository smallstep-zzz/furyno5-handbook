코드 검사와 NPU 실측의 구분

이번 핸드북 작성 환경에서는 RNGD에서 새 모델을 컴파일·실행하거나 새 성능 수치를 측정하지 않았다. 호출 API·정의 파일·CLI 구성·버전·실행 전제를 소스와 대조하고, 완전한 Python 예제의 문법을 검사했다. 예를 들어 5장의 병렬 컴파일 예제는 소스가 spawn 방식의 프로세스를 사용함을 확인하고 main() 보호를 추가했다. 이는 재현성을 높이는 코드 검토 결과이지 NPU 통과 결과는 아니다. 프로세스 생성 구현권한 필요

8장의 Schedule Viewer 수치는 컴파일러가 만든 정적 schedule의 비용이다. 실제 host 대기·전송·장치 상태·요청 분포를 포함한 benchmark 결과로 바꾸어 읽지 않는다. Schedule Viewer 설명

7장과 16장의 기존 성능 값은 해당 저장소의 보고서와 원자료를 설명한 것이다. 특히 FuryBoost는 NPU 측정값과 CPU 비교값의 tree 설정·threads·데이터 준비 범위·반복 조건을 함께 읽어야 한다. 하나의 kernel 개선과 전체 학습 시간 개선을 같은 값으로 취급하지 않는다. FuryBoost 비교 원자료권한 필요, histogram 변경 전후권한 필요

예제마다 다음 범위를 구별한다.

표기·형태 독자가 할 수 있는 해석
완전한 .py 예제 명시한 패키지·장치·파일을 준비하고 독립 스크립트로 재현할 수 있도록 구성했다. 이 문서에서 NPU로 검증했다는 뜻은 아니다.
“핵심 발췌”·함수 내부 fragment 원본의 책임과 중요한 동작을 설명한다. 주변 정의·인수·호출자가 별도로 필요하다.
“의사코드”·설계 표 변경 방향이나 계약을 설명한다. 아직 존재하지 않는 API를 실행 명령처럼 제시한 것이 아니다.
“기존 실측” 원자료에 남은 결과다. 조건·단위·측정 범위를 유지해야 비교할 수 있다.
“미확인”·“개발 과제” 공개 근거 또는 구현·검증이 충분하지 않다. 완료된 기능으로 의존해서는 안 된다.

재현 결과에 남길 최소 기록

먼저 어떤 프로그램을 어떤 환경에서 어떤 기준으로 검증했는지를 고정한다. 이 순서는 비교를 가능하게 하기 위한 핸드북의 권장 방법이며 모든 서비스에 같은 최적화 우선순위를 강요하는 규칙은 아니다.

  1. 환경: SDK·compiler·driver·firmware·Python·Torch 버전, 프로젝트 commit, 장치 수·PE 구성·mesh, host CPU와 NUMA 배치.
  2. 의미: 모델·가중치 revision, shape·dtype·stride, mask·상태 갱신 의미, reference 구현, 허용오차와 과제 품질 기준.
  3. 산출물: 생성한 TCL·EDF·package·실행 계획의 해시, compiler flags, 입출력 ABI, bucket 집합, 외부 weights 참조.
  4. 실행 증거: 준비·적재·실행의 성공 또는 실패, 실제 NPU Task, CPU fallback 정책, 반복 실행·새 입력·새 프로세스 적재 결과.
  5. 성능 범위: 컴파일·첫 로드·warm 실행·전체 요청을 분리한 시간, 전송 포함 여부, 동시성·요청 분포, 메모리 peak, 지연 분포.

정답이 일치하는 것과 NPU에서 계산한 것은 서로 다른 질문이다. 반대로 NPU Task가 보인다고 모델의 의미가 맞는 것도 아니다. 둘을 함께 확인하는 절차는 5장, 성능 측정의 축은 7장, 이식 실습의 완료 기준은 13장에 연결되어 있다.

수정할 때 지켜야 할 규칙

새 버전의 지원 범위를 추가할 때는 기존 설명을 조용히 덮어쓰기보다 변경된 버전·코드·검증 범위를 같이 남긴다. 문서와 코드가 다르면 어느 쪽이 어떤 시점을 나타내는지 적는다. 최신 브랜치 링크만 남기면 같은 주장을 나중에 재검토하기 어려우므로 중요한 구현과 시험 결과는 커밋을 고정한다.

공식 풀네임을 확인하지 못한 약어는 확장하지 않는다. EDF, eISA에 대한 이 책의 경계가 여기에 해당한다. TCL은 Tensor Contraction Language, PERT는 PE Runtime으로 공식 확인되었으며 용어사전에 명시했다. 새 근거가 생기면 출처와 함께 업데이트한다.
